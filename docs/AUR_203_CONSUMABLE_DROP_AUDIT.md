# AUR-203 consumable drop audit

Status: read-only code audit and technical proposal, 2026-11-24. No runtime changes or new tests were made for this audit. The new64 material package remains frozen. Proposed probabilities below are implementation starting values, **not owner-agreed balance**.

## Finding

The current ordinary death path drops equipment and materials, grants kill gold separately, and never creates potion drops. Potions already work as character counters; there are no reusable potion item definitions in `ITEM_DEFS`. Adding `{id:'hpPotion'}` or `{id:'mpPotion'}` to the existing drop array alone would fail: creation and reload normalization reject them because `itemDefinition` returns `null`.

A small ground-loot adapter can make these existing consumables collectible for exactly the new84 ordinary species while keeping the equipment catalogue, old257 species, all boss paths, shops, crafting and daily rewards unchanged. Potions should enter `hero.potions`, not the60-slot equipment/material inventory.

## Proposed minimum integration

1. Add a small pure module, proposed `js/loot/aur203ConsumableDrops.js`, containing two **ground-loot-only** descriptors for the already-used IDs `hpPotion` and `mpPotion`. Fields: RU/EN/ES names, `slot:null`, `consumable:true`, `resource:'hp'`/`'mp'`, `level:1`, `saleValue:0`. Do not add them to `GENERATED_ITEMS`, `ITEM_DEFS`, merchant stock, crafting, material maps, or shared inventory. Reuse existing SVG icons. Export definition/name helpers for ground-loot consumers.
2. Gate the extra reward by `!kind.boss` and exact membership of `kind.loot` in the union of `AUR203_MATERIAL_BY_LOOT` and `AUR203_EXPANSION_MATERIAL_BY_LOOT` (20+64). These are pure ID maps, so this avoids importing monster/art/runtime registries or using a broad string prefix. Validate that their union has exactly84 unique IDs before integration. No old257 or boss may enter this branch, even if an archetype is shared.
3. In `MonsterSystem.hit`, retain the existing `rollEncounterLoot(this.hero,m.kind)` call unchanged. Afterwards append zero or one extra consumable from a helper receiving the actual `m`, `deathAt` and base drop list. Use an isolated deterministic pseudo-random value derived from a versioned namespace, the existing unique monster event key and `deathAt` (for example a specified32-bit hash/mixer). **Never call `Math.random` or the equipment/material RNG for this extra roll.** This preserves both current-kill selection and subsequent global RNG consumption. Identical death-event input yields identical extra reward; a new respawn death gets a new seed. Document the hash algorithm and version so reload/retries cannot silently change results. Test injection can supply boundary values without touching production RNG.
4. In `groundLoot.js`, introduce `groundDropDefinition(item)` resolving existing `itemDefinition(item)` first and then the two exact potion descriptors. Use this resolver in normalization, pending normalization and materialization, so drops/pending jobs survive save/reload. Existing item records and quantity bounds retain their behavior. A ground-only potion lookup prevents potion IDs from accidentally becoming ordinary bag materials with stack100 or sale rules.
5. Add an explicit potion branch to `pickupGroundDrop` **after existing missing/range/life/reentrancy checks and before inventory insertion**. Resolve resource only through the fixed descriptor, calculate available capacity `max(0,99-currentCount)`, and credit `hero.potions[resource]`. Copy/snapshot the original potions object before mutation, including whether it originally existed. Remove/reduce the ground drop and call the same synchronous save exactly once. On false/throw restore both original potion state and the entire original drop; retain the WeakSet guard. Do not mutate HP/MP, gold, inventory, cooldown, shops or quests.
6. Change `LootPanel.update` to use the ground resolver/localized ground name helper for its ground rows, and `GroundLootSystem.tryPickup` to use the same name helper for notifications. Pass the resolved descriptor into existing `itemArt`; the existing icon router already understands the IDs. Add a localized `potionCapacity` failure message in the ground-loot panel/system copy only. Do not reuse the inaccurate inventory-full message for a99-counter cap. Chest markers can remain unchanged.

### Explicit balance proposal

One isolated uniform value per eligible ordinary death: `[0,.04)` yields oneHP potion; `[.04,.06)` yields oneMP potion; `[.06,1)` yields none. Maximum one potion per death, common rarity, quantity1, independent of luck/class/level/material success and available inventory/counter capacity. This is4%HP and2%MP,6% combined, with no equipment or material chance reduction. Expected4HP/2MP per100 eligible kills. These values are a technical starting proposal requiring owner balance review; they are not reported as existing or agreed behavior.

Capacity must affect **pickup**, never whether a drop is rolled. Otherwise a full counter destroys a reward before the player can consume a potion and return.

## Required edge-case semantics

- **Inventory full:**60 occupied inventory slots do not block counter-based potion pickup; equipment/material pickup still follows existing capacity rules. A take-all operation can report full for equipment and still collect later eligible potion drops.
- **Potion cap:** a counter at99 or above rejects that resource with `potionCapacity`; leave the drop unchanged. Do not clamp/reset an imported existing value above99. For quantity1, normal and take-all are identical. For normalized multi-quantity records, preserve existing transaction semantics: single pickup requires the whole quantity to fit; take-all credits only available room, saves the remainder on ground, and never exceeds99.
- **Touch/radius:** no HUD auto-credit on kill. Tap the existing chest marker within180, identify HP/MP by localized name and red/blue icon, then Take/Take all. Beyond180, wrong region, dead hero, hidden/blocked state and open gameplay panels retain existing rejection rules.
- **Reload without duplication:** successful pickup saves potion count and removal/remainder in the same character JSON. Reload sees either the prior drop/count or the new count/removal. The event timestamp remains after collection, preventing recreation for the same death. Repeat pickup returns missing. Pending placement jobs retain the already-rolled potion record and never reroll. New respawn death remains a distinct legitimate event.
- **Save failure:** pickup restores counters and full source drop on false/throw before success UI. No claim of durable success is made. The current death-creation path already calls `scene.save()` but does not roll its in-memory kill/drop state back on failure; keep retries using the stored rolled job/event. A later successful pickup save also persists the associated monster death/event. If the tab closes before any successful save, reload returns to the earlier persisted state; unsaved kills/rewards are not promised to survive. This existing limitation should be described accurately rather than calling all mutations atomic.
- **No asynchronous save promise:** current transactions interpret any return except false as success. Continue to require synchronous boolean `WorldScene.save`/`Save.write`; do not pass a Promise without redesigning transaction handling.

## Blockers and focused validation before enabling

There is currently no potion definition recognized by ground persistence, no potion-counter pickup branch, and no cap-specific ground UI feedback. These are concrete implementation blockers, not missing artwork: red/blue icons and consumption already exist. The new84 exact runtime whitelist must include both first20 and next64 only once; all84 species/art readiness is a separate root integration gate. A stable hash/version and explicit probabilities must be recorded as technical balance choices before release.

After the root's current test freeze is lifted, add focused checks for: all84 eligible and all old257/bosses ineligible; unchanged existing RNG call trace and output before/after potion augmentation; deterministic event seed; chance boundaries; recognized potion creation/pending/reload; inventory-full success; cap99 rejection; both partial and full quantity policies;180 boundary/wrong region/dead hero; false/throw/reentrant save rollback; successful Save.write/load retaining counters/removal/death-event; duplicate pickup/death prevention and distinct respawn death. Browser checks should exercise touch identification and localStorage quota failure using real scene save, not a no-op callback. Existing potion consumption, merchant price10/cap99, daily10HP/5MP, equipment tables/catalogue and boss loot tests must remain unchanged and pass.
