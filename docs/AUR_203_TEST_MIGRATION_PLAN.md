## Минимальное разделение областей проверки

Нужен один тестовый helper, например `tests/worldExpansionScope.mjs`, с двумя разными обязанностями:

1. `originalTask10Camps(content)` выбирает лагеря по ID из неизменной фикстуры, проверяет точный исходный порядок и полноту, возвращает их. Не использовать диапазон координат, произвольный `slice(0,257)` или только регулярное выражение: стартовый лагерь имеет исторический ID `forest-starter-wolves`.
2. `assertActiveExpansion(content, expectedReadyIds)` проверяет **полный настоящий runtime**. Его ID должны точно равняться исходным ID плюс явно принятым к этому этапу новым ID. На первом этапе ожидаются ровно 20 перечисленных видов и 220 новых особей; более поздние этапы требуют отдельного проверяемого изменения ожидаемого списка.

Ожидаемые числа нельзя получать из того же `getRegionContent().camps.length`, который проверяется. Нужны явный список принятых видов и независимые фиксированные итоги этапа. Для полного списка сверяются уникальность camp/spawn/species ID, отсутствие лишних объектов, 11 особей, диапазоны уровней, настоящий artwork, работающие способности, добыча, сохранения и отсутствие дубликатов текстур. Старый helper не заменяет эту новую полную проверку.

## Реестр ассетов и каталоги

`js/assets/speciesAssets.js` строит `bySpecies` **только из `TASK10_LAYOUT`**. Поэтому `uniqueSpeciesEntries()` намеренно остаётся 257 даже после добавления записей в `INTEGRATED_SPECIES_ART`. Это удобный сохранённый контракт, но не глобальный счётчик AUR-203.

Минимальный вариант — сохранить существующие Task10-функции, а для активного открытого мира добавить отдельный API, использующий только зарегистрированные **и действительно активированные** ID. Не считать все файлы или все art-only descriptors готовыми видами. Не создавать циклический импорт `speciesAssets → regionContent → speciesAssets`: общий чистый readiness-список либо явный аргумент с активным контентом безопаснее.

`scripts/generate-species-catalog.mjs` сейчас обходит все `getRegionContent().camps`, но жёстко записывает 257/2827. После append это создаст противоречивый каталог: новые строки получат `primary:null`, поскольку `uniqueSpeciesArt` имеет область Task10. Нужно выбирать исходные лагеря по неизменному списку ID и требовать ровно 257 строк; существующий Task10 JSON/MD и `--check` сохраняют свой смысл. Новый каталог AUR-203 должен отдельно показывать принятые виды, реальные ассеты/AI/loot и оставшиеся незавершённые ID, не выдавая их за готовые.

`getRegionContent()` использует `!uniqueSpeciesArt(id)` для `temporaryBestiary`; для добавленных AUR-203 видов нельзя автоматически наследовать это Task10-ограничение. `monsterArt()` уже берёт зарегистрированные виды из `INTEGRATED_SPECIES_ART`, поэтому фактическая картинка может быть готова, а флаг ошибочно останется «временная». Проверка нового активного вида должна связывать оба результата с одной принятой записью.

Глобальная проверка для первого этапа должна требовать ровно 277 уникальных ID, texture keys, image URLs, atlas URLs и SHA изображений; для всех моделей — 48 действительных кадров/8 направлений, прозрачность, опоры и настоящий runtime renderer. Файловая уникальность не доказывает художественную уникальность: native QA и браузерная проверка остаются обязательными. `tests/preservedSpeciesArt.mjs` продолжает защищать прежние 257, но его Task10-only проверка уникальности не обнаружит конфликт нового ключа со старым — его должен ловить новый глобальный тест.

## Геометрия, индексы и производительность

- `js/world/aur203Layout.js:buildAur203Region` намеренно отвергает `content.camps.length !== config.first`. После append передавать ему проверенную исходную проекцию, сохраняя все нынешние дороги/NPC/приёмники/17 входов. Не ослаблять guard, чтобы повторная генерация произвольно сдвинула зарезервированные позиции.
- SHA файла `aur203Placements.js` остаётся `652108eb4845b44f47163c726dc59f084f1d0d83cde84afd11730d24ee98f945`. Проверять полный набор 84 мест, даже когда активна лишь часть. Реальную проходимость и патрулирование дополнительно проверять на **актуальной** карте с активными лагерями и фактическим радиусом нового вида.
- Старый `task10Spots` использует `movementProfile(MONSTER_TYPES[camp.type])`. Для новых видов с descriptor/trait overrides фактический радиус следует получать через `movementProfile(monsterKind(spawn))`, иначе геометрический тест может незаметно проверять другой профиль.
- `browser-soak.cjs` выбирает `c.camps[Math.floor(c.camps.length/2)]`: append меняет контрольную точку. Сохранить прежний средний лагерь по ID и добавить отдельные новые точки. Все лимиты памяти/объектов/текстур сохраняются.
- `browser-task9-performance.cjs` посещает `c.camps.at(-1)`: теперь это новый лагерь, а прежняя хвостовая точка пропадает из сравнения. Сохранить старый tail ID и добавить новый tail, чтобы сравнение до/после оставалось объяснимым.
- `browser-monster-stream.cjs` может использовать `work/stream-benchmark/content-baseline.json` вместо текущего мира и по умолчанию строит только три региона. Оставить сопоставимый baseline, но отдельно проверять настоящий четырёхрегионный набор AUR-203; иначе тест не подтверждает новые пустынные споты.
- `regionRoads` использует уже заданные точки дорог, но `naturalRoadPoints` зависит от лагерей, если его вызвать заново. Не перегенерировать старые дороги. Новые лагеря влияют на clearing/reservation декоративных объектов в `describeChunk`; визуальную геометрию возле важных старых точек нужно сравнить на реальном runtime, а не только на отфильтрованной тестовой копии.

## Новые проверки перед включением первого набора

1. Для каждого из 20 принятых ID — настоящий camp + 11 spawn descriptors + зарегистрированный artwork + RU/EN/ES + реальные ability/behavior configs + тематический loot; отсутствуют только подготовленные, но не активированные 64 ID.
2. Все исходные 257 контракта сохраняются, а список всего runtime равен точно принятому расширению. Каждая новая способность действительно выпускается и воздействует на игрока; guard/retreat/pack — не просто поля каталога. Старые виды без opt-in ведут себя прежним образом.
3. Новые бой/смерть/30 секунд/занятый респавн/выгрузка чанка/reload/наземная добыча проверяются в реальном движке. Во всех трёх слотах сохраняются старые персонажи, новые смерти/предметы не дублируются, старые цели заданий остаются доступны.
4. Проходимость, патрульные альтернативы, LOS, радиусы/территории и разделение соседних спотов проверяются с действительными новыми профилями. При невозможности разместить более крупный профиль менять/проверять новый вид, а не молча сдвигать старые объекты.
5. Текстуры загружаются по расстоянию и освобождаются, включая быстрые смены регионов; сравниваются одинаковые старые и новые маршруты. Не увеличивать существующие лимиты ради зелёного результата.
6. Каталог экипировки/его уровни/характеристики и старые rarity/boss RNG остаются защищены. Если новым видам потребуются новые материалы, расширять отдельный add-only каталог и адаптировать точные счётчики `task10StoneGiantRewards`/`thematicMaterials` с сохранением прежних определений и прежних RNG-фикстур; не регенерировать старые фикстуры под новые результаты.
7. Публикация сообщает точное фактическое количество текущего этапа. Отдельно фиксируются Android Chrome viewport-тесты и ограничения; физическая Android-приёмка остаётся владельцу.
